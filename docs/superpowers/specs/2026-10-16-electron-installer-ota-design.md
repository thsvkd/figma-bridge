# 피그마 연결: Electron 설치판과 OTA 설계

작성일: 2026-10-16. 상태: 승인 대기.

## 1. 의도와 배경

지금의 피그마 연결은 PowerShell 스크립트, WinForms GUI, Bun으로 실행하는 중계 서버(`lib/relay.js`)로 이루어져 있고, 설치는 `설치.cmd`를 더블클릭하는 방식이다. 이 구조는 다음 문제가 있다.

- Bun과 winget에 의존해서 사용자 환경에 따라 설치가 깨질 수 있다.
- 릴리스에 설치 파일이 없고, 새 버전이 나와도 사용자가 알 방법이 없다.
- 켜기와 끄기를 하나의 스위치로 다루지 못한다.
- 플러그인 실행이 고정 대기 시간에 의존해서 느리고 불안정하다.

목표는 디자이너와 개발자가 `setup.exe` 하나를 받아 설치하고, 연동 버튼 하나만 눌러 곧바로 쓰게 만드는 것이다. 이후 새 버전은 앱이 알려 주고 사용자가 누르면 갱신된다. 참고 사례는 `thsvkd/ftp-browser`(Electron, electron-builder, electron-updater, GitHub Release)다.

## 2. 목표, 비목표, 반목표

**목표**

1. GitHub Release에 Windows용 `setup.exe`가 올라가고, 사용자는 그것 하나로 설치한다.
2. ftp-browser 방식의 OTA 업데이트를 제공한다.
3. 연동은 버튼 한 번으로 끝나고, 켜기/끄기 스위치로 끄고 켤 수 있다.
4. 피그마 플러그인 실행은 지금의 방식(창을 앞으로 가져와 키 입력을 보냄)을 유지하되 빠르고 안정적으로 만든다.
5. 모든 연동 동작은 멱등하다. 같은 동작을 반복해도 결과가 같다.

**비목표**

- Mac, Linux 지원. 이번에는 Windows만 지원한다.
- 코드 서명. 서명 없이 배포하며, SmartScreen의 "알 수 없는 게시자" 경고를 감수한다. 설치 안내문에 경고를 넘기는 방법을 적는다.
- 플러그인을 키 입력 없이 실행하는 방법의 탐색. 사용자가 현재 방식 유지를 결정했다.
- 포터블 버전 제공. 설치판만 만든다.
- 서드파티 Talk to Figma 플러그인 자체의 수정. 플러그인은 지금처럼 피그마 커뮤니티의 것을 쓴다.

**반목표** (기술적으로 동작해도 실패로 보는 경우)

- 연동 버튼을 눌렀을 때 이미 붙어 있는데도 피그마 창을 앞으로 가져오거나 키를 보내는 것.
- 연동을 반복해서 누르면 MCP 항목이 중복되거나 중계 서버가 둘 이상 뜨는 것.
- 끄기를 눌렀을 때 사용자의 AI 도구 설정이 지워지는 것.
- 업데이트가 사용자가 누르기 전에 앱을 멋대로 종료하거나 재시작하는 것.
- 로그인 자동 시작이나 업데이트 후 재시작 때문에 사용자가 다른 작업을 하는 중에 피그마가 실행되거나 포커스를 빼앗기는 것.
- 플러그인이 붙어 있지 않은데 화면이 "연결됨"처럼 보여서, 사용자가 AI 도구에서 실패한 뒤에야 알게 되는 것.

## 3. 제약

- 운영체제는 Windows 10 이상, 64비트. 설치에 관리자 권한을 요구하지 않는다(사용자 단위 설치).
- 피그마에는 플러그인을 외부에서 실행하는 공식 API가 없다. 따라서 창 포커스와 키 입력 자동화(`user32`, 퀵 액션 `Ctrl+/`, 마지막 플러그인 재실행 `Ctrl+Alt+P`)가 계속 필요하다.
- 피그마 플러그인이 설치되어 있는지 직접 알아낼 공식 방법이 없다. 설치 여부는 "플러그인이 중계 서버에 붙었는가"라는 결과로만 판단한다.
- 중계 서버 포트는 기존과 같이 `127.0.0.1:3055`다. 이 포트는 플러그인이 고정으로 접속하므로 바꿀 수 없다.
- 코드 서명이 없으므로 자동 업데이트의 무결성은 `latest.yml`의 해시 검증에만 의존한다.

| D11 | 자동 테스트는 플러그인이 이미 설치된 경우와 설치되지 않은 경우를 모두 다루고, 멱등성을 검증한다. |

## 5. 설계

### 5.1 구성 요소

기능은 아래 경계로 나눈다. 각 경계는 주입 가능한 인터페이스로 만들어서 테스트에서 가짜로 교체한다.

- **Relay**: `relay.js`의 동작을 Node(`ws`)로 옮긴 중계 서버. 채널 브리지와 `GET /status`를 유지한다. 플러그인과 AI 도구를 구분하는 기존 규칙(Origin이나 User-Agent 헤더 유무)을 그대로 쓴다.
- **McpRegistry**: Claude Code(`claude mcp add --scope user`), Claude Desktop(JSON 설정), Codex(TOML 설정)에 `TalkToFigma` 항목을 등록하고 확인하고 제거한다. MCP 서버는 설치된 앱 실행 파일을 `ELECTRON_RUN_AS_NODE=1`로 호출해서 번들된 `cursor-talk-to-figma-mcp@0.3.5`를 실행하게 등록한다.
- **FigmaDriver**: 피그마 설치와 실행 여부 확인, 창 앞으로 가져오기, 키 입력 전송, 포커스 복원을 맡는다. 테스트에서는 이 경계를 가짜로 바꾼다.
- **PluginLauncher**: FigmaDriver와 Relay 상태를 이용해 플러그인을 붙이는 절차를 조정한다(5.3 참고).
- **BridgeController**: 켜기/끄기 상태 기계. Relay, McpRegistry, PluginLauncher를 순서대로 호출하고 상태를 저장한다. 진입점은 둘이다. 사용자가 누르는 **켜기**는 플러그인 붙이기까지 실행하고, 앱 시작이나 업데이트 후 재시작에서 부르는 **복원**은 플러그인 붙이기를 실행하지 않는다.
- **UpdateManager**: `electron-updater`를 감싸는 작은 상태 관리자. 화면에는 상태 하나와 명령 몇 개만 노출한다(ftp-browser의 U3와 같은 이유).
- **UI**: 메인 창(연동 스위치, 상태 줄, 업데이트 알림, 설정)과 트레이 아이콘.
- **Doctor**: 기존 점검 기능을 이식한다. Bun 항목은 사라지고, 중계 서버, 피그마, 플러그인, 각 AI 도구의 MCP 등록을 결정론적으로 점검하고 고친다.

### 5.2 켜기와 끄기

**켜기** 순서는 다음과 같고, 각 단계는 이미 만족된 상태면 아무것도 하지 않는다.

1. 중계 서버가 우리 것으로 떠 있는지 확인하고, 아니면 시작한다. 3055를 다른 프로그램이 쓰고 있으면 사용자에게 원인을 알린다.
2. 설치된 AI 도구마다 MCP 항목을 확인하고, 없거나 다르면 갱신한다. 이미 올바른 항목이 있으면 건드리지 않는다. 항목이 앱 경로를 가리키므로 앱이 이동했거나 업데이트된 경우에도 이 단계에서 바로잡는다.
3. 플러그인을 붙인다(5.3).
4. 스위치 값을 켜짐으로 저장한다.

**복원**은 앱이 시작될 때(로그인 자동 시작 포함)와 업데이트 설치 후 재시작될 때 저장된 스위치 값이 켜짐이면 실행된다. 켜기의 1, 2단계(중계 서버, MCP 확인)만 수행하고, 3단계(플러그인 붙이기)는 하지 않는다. 다만 플러그인이 이미 붙는 경우를 위해 `/status`는 확인한다. 피그마가 실행 중이고 플러그인이 스스로 다시 붙으면 복원 직후 자연스럽게 연결된다.

**화면 상태**는 다음 셋으로 구분하고, 서로 확연히 다르게 보여야 한다.

- **꺼짐**: 중계 서버가 멈춰 있다.
- **중계 켜짐, 플러그인 미연결**: 중계 서버와 MCP는 준비됐으나 피그마 플러그인이 붙지 않았다. 주의를 끄는 색과 문구로 "아직 연결되지 않았습니다"를 분명히 알리고, 같은 자리에 **플러그인 연결** 버튼을 둔다. 이 버튼은 5.3의 절차를 실행한다. 트레이 아이콘에도 이 상태를 반영하고, 트레이 메뉴에 같은 동작을 둔다. 이 상태에서 시스템 알림 등으로 사용자를 방해하지는 않는다.
- **연결됨**: 중계 서버가 떠 있고 플러그인이 붙어 있다.

플러그인이 나중에 끊기면(피그마 파일을 닫는 경우 등) 화면은 두 번째 상태로 돌아가고, 다시 붙으면 세 번째 상태가 된다. 상태는 `/status`를 짧은 간격으로 읽어서 갱신한다.

**끄기**는 중계 서버를 멈추고 스위치 값을 꺼짐으로 저장한다. MCP 항목은 남겨 둔다. 끈 상태에서 AI 도구는 연결이 끊긴 것으로 보일 뿐 설정은 깨지지 않으며, 켜면 곧바로 복구된다.

앱을 완전히 제거할 때만 MCP 항목을 제거한다(설치 프로그램의 제거 단계).

### 5.3 플러그인 붙이기 (빠르고 안정적으로)

절차는 다음 순서다. 앞 단계에서 붙으면 뒤 단계는 실행하지 않는다.

1. 이미 플러그인이 붙어 있으면(`/status`의 `figmaJoined`) 아무 입력도 보내지 않고 끝낸다.
2. 피그마 앱이 없으면 설치 안내로 끝낸다. 실행 중이 아니면 실행하고, 창이 나타날 때까지 기다린다.
3. 창을 앞으로 가져오고 포커스를 얻었는지 확인한다. 얻지 못하면 한 번 더 시도한다.
4. 퀵 액션(`Ctrl+/`)으로 플러그인 이름을 입력해 실행하고, 붙었는지 확인한다.
5. 안 붙으면 마지막 플러그인 재실행(`Ctrl+Alt+P`)을 시도하고, 붙었는지 확인한다.
6. 그래도 안 붙으면 플러그인이 설치되지 않은 것으로 보고, 피그마 앱 안에서 플러그인 설치 페이지를 연다. 사용자가 Run을 한 번 누른 뒤 다시 연동하면 위 절차가 다시 돌고, 1단계에서 끝난다.
7. 어느 경우든 끝나면 사용자가 보던 창으로 포커스를 돌려준다.

속도와 안정성의 기준은 다음과 같다.

- 단계 사이의 고정 대기 대신, "창이 보인다", "포커스가 옮겨졌다", "플러그인이 붙었다" 같은 조건을 짧은 간격으로 확인하며 기다린다. 각 조건에는 상한 시간을 둔다.
- 키 입력은 포커스가 피그마 창에 있다고 확인된 직후에만 보낸다. 포커스를 잃으면 입력을 중단하고 실패로 처리한다.
- 구체적인 대기 시간과 재시도 횟수는 구현자가 실측으로 정한다(6절 참고).

### 5.4 설치와 릴리스

- `electron-builder`로 NSIS 설치 파일을 만든다. 사용자 단위 설치이며 관리자 권한이 필요 없다. 바탕화면과 시작 메뉴에 바로가기를 만든다.
- 제거 단계는 설치 파일을 지우고, 사용자가 등록한 MCP 항목을 제거한다. 런타임 데이터와 로그(`%LOCALAPPDATA%\FigmaBridge`)를 지울지는 제거 화면에서 묻는다.
- 릴리스는 `v*` 태그를 올리면 GitHub Actions(`windows-latest`)가 빌드하고 `*-setup.exe`, `*-setup.exe.blockmap`, `latest.yml`을 하나의 GitHub Release에 올린다.
- 설치 파일 이름과 `latest.yml`은 ftp-browser의 규칙을 따른다.

### 5.5 OTA 업데이트

- `electron-updater`를 쓰고 publish provider는 `github`(owner/repo)로 한다. `generic`과 `releases/latest/download` 조합은 차등 업데이트를 조용히 무력화하므로 쓰지 않는다(ftp-browser 함정 A).
- `autoDownload`와 `autoInstallOnAppQuit`을 모두 끈다. 확인은 앱을 시작할 때 한 번 하고, 설정 화면에 수동 확인 버튼을 둔다.
- 새 버전이 있으면 메인 창에 알림을 띄우고 트레이로도 알린다. 알림이 다운로드를 시작하지는 않는다. 사용자가 누르면 다운로드하고, 다운로드가 끝나면 다시 눌러 재시작과 설치를 진행한다.
- 오류는 `checkForUpdates()`의 거부(rejection)뿐 아니라 `error` 이벤트로도 오므로 둘 다 처리해서 화면이 "확인 중"에서 멈추지 않게 한다(함정 B).
- 이미 받아 둔 업데이트(`ready`) 상태에서는 다시 확인하지 않는다(함정 C).
- 화면은 알림을 놓칠 수 있으므로, 설정 화면을 열 때 현재 업데이트 상태를 다시 읽는다(함정 D).
- 재시작과 설치 후에는 마지막 스위치 값이 켜짐이면 5.2의 **복원**이 실행된다. 플러그인 붙이기는 하지 않으며, 플러그인이 붙지 않았으면 "중계 켜짐, 플러그인 미연결" 상태로 보인다.

### 5.6 상태 저장

설정과 상태(스위치 값, 자동 시작 여부, 마지막 연동 결과)는 `%LOCALAPPDATA%\FigmaBridge`의 JSON 파일에 저장한다. 설정을 읽는 쪽은 알 수 없는 필드를 무시하고 없는 필드는 기본값으로 처리한다. 경로 규칙과 `FIGMA_BRIDGE_HOME` 환경 변수는 기존과 같이 유지한다.

## 7. 테스트 요구

- 자동 테스트는 FigmaDriver, Relay 상태, McpRegistry를 가짜로 교체해서 다음을 모두 검증한다.
  - 플러그인이 이미 붙어 있는 경우: 입력이 하나도 전송되지 않는다.
  - 플러그인이 설치되어 있고 퀵 액션으로 붙는 경우.
  - 퀵 액션이 실패하고 마지막 플러그인 재실행으로 붙는 경우.
  - 플러그인이 설치되지 않은 경우: 두 방법이 모두 실패하고 설치 페이지가 열리며, 이후 다시 연동하면 정상으로 이어진다.
  - 피그마가 없는 경우, 실행되지 않은 경우, 포커스를 얻지 못한 경우.
- 멱등성 테스트: 연동을 연속으로 두 번 호출해도 MCP 항목이 하나뿐이고, 중계 서버가 하나뿐이며, 두 번째 호출은 키 입력을 보내지 않는다. 끄기와 켜기를 반복해도 같은 결과가 나온다. 끄기는 MCP 항목을 건드리지 않는다.
- 복원 테스트: 저장된 값이 켜짐일 때 앱 시작과 업데이트 후 재시작을 흉내 내면, 키 입력과 피그마 실행과 창 앞으로 가져오기가 **0회**임을 단언한다. 중계 서버와 MCP 확인은 수행되고, 플러그인이 붙지 않았으면 상태가 "중계 켜짐, 플러그인 미연결"이다.
- 상태 표시 테스트: 꺼짐, 중계 켜짐 플러그인 미연결, 연결됨 세 상태가 `/status` 값에 따라 정확히 갱신되고, 플러그인이 끊기면 두 번째 상태로 돌아간다.
- Relay는 실제 WebSocket 연결로 채널 브리지와 `/status`를 검증한다(기존 `tests/relay-check.js`의 시나리오를 옮긴다).
- UpdateManager는 가짜 updater로 상태 전이를 검증한다(확인, 사용 가능, 다운로드, 준비 완료, 오류, `ready`에서의 재확인 차단).
- 실제 피그마를 쓰는 검증은 수동 체크리스트로 따로 남긴다. 플러그인을 설치한 상태와 설치하지 않은 상태 각각에서 연동을 두 번씩 눌러 확인하는 항목을 포함한다.

## 8. 내가 정한 것 (사용자 확인 필요)

아래는 대화에서 합의하지 않고 제가 기본값으로 정한 내용이다.

- 기술 구성은 TypeScript, electron-vite, electron-builder(NSIS), electron-updater, vitest다.
- 중계 서버는 Bun 대신 Node의 `ws` 라이브러리로 옮긴다. 동작은 `relay.js`와 같게 유지한다.
- Talk to Figma MCP 패키지는 앱에 번들해서 버전을 고정(`0.3.5`)한다. 처음 연동할 때 네트워크로 받지 않는다.
- 기존 AI 도구 설치 버튼과 AI 점검 기능은 기능을 유지한 채 이식한다.
- 플러그인이 설치되지 않은 경우의 안내는 "피그마에 열린 페이지에서 Run을 한 번 누른 뒤 연동을 다시 누르세요"로 한다.
- 설치 프로그램은 사용자 단위, 관리자 권한 없음, 한국어 안내다.
- 설치 안내문(README)에는 SmartScreen 경고를 넘기는 방법을 적는다.
- "플러그인 미연결" 상태에서는 시스템 알림 없이 창과 트레이 표시만 바꾼다. 사용자를 방해하지 않는다는 취지에 맞춘 것이며, 알림을 원하시면 바꿀 수 있다.
